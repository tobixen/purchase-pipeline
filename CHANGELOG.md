## [Unreleased]

### Added
- **First release: the purchasing pipeline now has its own project.** Receipt import, the staging schema, the purchases ledger, the commit pipeline and the Open Prices / Open Food Facts / tingbok publishers moved here out of `inventory-md/scripts/`, where they inverted the dependency — a general-purpose inventory tool knowing about one person's accounting and receipt formats. The diary↔ledger coverage check moved here too, from `~/bin`, where it lived because it belonged to neither project.
- **Everything is a console script**: `shopping-context`, `receipt-formats`, `shop-import`, `purchase-pipeline`, `purchase-ledger`, `staging-to-inventory`, `tingbok-push`, `off-upload`, `osm-resolve`, `osm-add-shop`, `osm-auth`, `openprices-publish`, `openprices-auth`, `check-grocery-ledger`. No more `~/inventory-md/scripts/foo.py` paths to remember or allowlist.
- **A staging file must balance**: its line items have to sum to `receipt_total`, or every consumer refuses it. Transcribing a photographed receipt is the only point in the pipeline where a human reads numbers off an image, and the sum is the only cross-check that exists for that reading.
- **The workflow guide moved here too** (`claude-skills/process-shopping.md`, from `inventory-md/claude-skills/`) — it is a manual for this project, and all but three of its commands are this project's. The duplicated item-adding reference it carried (the `inventory-md add` / `inventory-md edit` blocks) is gone in favour of pointing at inventory-md's `docs/ADDING-ITEMS.md`, which is where the item-line format, field reference, categories, tags and best-before conventions belong.
- **`osm-resolve`** answers "which OSM object is this shop, and is it mapped at all?" in one command — `--lat/--lon/--name` lists what Overpass finds within a radius, ranked by name similarity and distance, each with a map link to eyeball. Confirming a candidate is still yours to do in a browser; `--save-as KEY --pick TYPE:ID` records the answer afterwards. It replaces the reverse-geocode `openprices-publish --suggest-from-photo` used to print, which answered a different question and once suggested the wine shop next door; that flag is now `--coords-from-photo` and prints a photo's GPS as an `osm-resolve` command to run.
- **`osm-add-shop`** puts a surveyed shop on the map when `osm-resolve` finds it is not there — one node per run, dry-run by default, authorised by a token from the new `osm-auth`. Adding a shop is the only genuinely public write in this pipeline, so it is the most guarded: the duplicate check has no blanket override (each nearby object must be waved off individually, after you have looked at its map link), coordinates must be precise enough to have come from a GPS rather than a keyboard, and the changeset says plainly that it is a survey uploaded by a script. There is no batch mode, deliberately.
- **A cached shop must name a branch.** `Billa Sozopol ул. Републиканска 5` is a key; `Billa` is refused, because a price has to point at one store and a chain-only key would quietly resolve to whichever branch was saved first. Repointing an existing key needs an explicit override too.
- **The Lidl receipts file is no longer a mystery**: the README and the workflow guide now say where `~/regnskap/lidl_receipts.json` comes from, and `shop-import` records a receipt's own `source` stamp in the staging file rather than just the filename it sat in. Fetching it belongs to [order-scrapers](https://github.com/tobixen/order-scrapers) (`lidl-history --fetch`), not here.
- **A staging file arrives with `ean` and `bb` already filled** where the evidence settles it, so the review step is left with the genuinely undecided lines instead of all of them. A scanned barcode fills a line when that line's own `ean_candidates` already carried the EAN — two independent sources agreeing — and a repeat purchase with no photo at all is filled from a candidate scoring 1.0, an exact prior observation of that till string rather than a similarity guess. A best-before travels with the match, including one shot in the frame after the barcode. Every filled field records what filled it in `ean_source`/`bb_source`, so a reviewer can tell the importer's claim from their own work.
- **What is not settled is now visibly unsettled.** An unplaceable scan stays in `loose_photos` with a `review` line saying what stopped it (no receipt line lists this EAN — a new purchase; or several do), and `shop-import` prints the list on the way out. A photo whose barcode decoded two parity-confusable ways arrives as one `barcode_conflict` entry carrying **no** `ean`: every candidate has a valid check digit, because a parity misdecode recomputes the checksum over the corrupted digits, so this is a read-the-digits job and not a pick-the-first. Previously `shop-import` ignored the extractor's review verdict entirely and wrote the first read in as if it were certain — and reported a losing, already-rejected read as a photo of its own.
- **`purchase-pipeline` takes a whole day's shopping at once** — `purchase-pipeline A.yaml B.yaml C.yaml --commit` runs each file's commit stages in order and validates once at the end, instead of re-parsing and re-quality-checking the whole of `inventory.md` after every file at about two minutes a go (three shops in one day is a normal Saturday, and those runs had to be backgrounded and hand-serialised to keep them off each other's `inventory.json`). Each file is still its own reviewed gate: the status block advances per stage, and a failure stops the run there with the later files not started and nothing validated over a half-written inventory. `--no-validate` skips the closing gate for a caller who will run it themselves. Batching *files* is not batching *writes* — `osm-add-shop` still refuses to do more than one shop, because that one writes to a shared public database.
- **`--from` no longer revives a `skipped` stage.** It re-runs `done` stages — that is what a restart is for — but `skipped` is the reviewer's decision that a stage must never run for that file. The difference only became load-bearing with several files per invocation, where `--from ledger` would otherwise have pushed a hardware trip marked `tingbok_push: skipped` to tingbok as a side effect of re-running the ledger stage on the other two.
- **`receipt-formats`** records per-chain receipt layout quirks — which address line names the branch, whether an `N x unit_price` multiplier belongs to the line above or below it, how discounts and deposits print — and prints them as a checklist before transcription.
